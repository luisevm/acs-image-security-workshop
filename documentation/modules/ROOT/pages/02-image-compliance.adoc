= Step 2 - Image Compliance: Alert first, then block
include::_attributes.adoc[]

Step 1 left you with a policy that reports. In this step you add three image rules: no `latest` tag, only approved registries, and no image older than 365 days. All four policies send their violations to a webhook receiver running in the cluster. You run them in inform mode first, so you can see what they would catch, then switch them to enforce and watch the admission controller reject new deployments, updates, and scaling of workloads that break them. You finish with the break-glass annotation, which lets an emergency deployment through and records that it happened.

== Prerequisites

* xref:01-inventory-cve.adoc[Step 1] completed: `legacy-app` and `current-app` run in `acs-image-demo` and the CVE policy exists
* `source myenv.sh` run in your current shell

== How it works

The policies cover two lifecycle stages. At the BUILD stage, `roxctl image check` and `roxctl deployment check` evaluate them on demand. At the DEPLOY stage, the ACS admission controller (a validating webhook) evaluates every create, update, and scale request in scope.

A policy without enforcement actions only creates violations and notifications. Adding enforcement actions makes ACS act: `FAIL_BUILD_ENFORCEMENT` makes `roxctl image check` exit with an error, the `FAIL_DEPLOYMENT_*` actions make the admission controller reject the request, and `SCALE_TO_ZERO_ENFORCEMENT` lets Sensor scale a violating deployment to zero replicas if it gets past admission, for example after a webhook timeout.

== What this solves

[cols="2,3",options="header"]
|===
| Problem from Step 1 | How this step solves it

| Nobody is notified when a violation appears
| Every workshop policy sends its violations to a notifier

| Vulnerable, outdated, or untrusted images can still be deployed
| The admission controller rejects creates, updates, and scaling that break an enforced policy

| A pipeline can still build and push a non-compliant image
| `roxctl image check` exits with an error when an enforced policy is violated
|===

| Approach | Notes

| ACS policies with admission enforcement (this step)
| Can use image content (CVEs, image age) as well as the image reference. Uses the scan data ACS already has.

| OPA Gatekeeper, Kyverno, or ValidatingAdmissionPolicy
| Good at rules on the pod spec, such as the tag or the registry. CVE or image-age decisions need an external data source.

== Reset

This returns the cluster to the state at the end of Step 1. The test workloads go first, then the three new policies, then the CVE policy goes back to its Step 1 version without the notifier. The notifier and the receiver go last, because Central should not hold a policy that points to a deleted notifier.

[.console-input]
[source,bash]
----
# 1. Test workloads (some were never created)
oc --context hub delete -f 02-image-compliance/tests/ --ignore-not-found

# 2. Policies added in this step
oc --context hub delete securitypolicy workshop-latest-tag workshop-trusted-registries workshop-image-age \
  -n stackrox --ignore-not-found

# 3. CVE policy back to the Step 1 version (inform only, no notifier)
oc --context hub apply -f 01-inventory-cve/04-policy-fixable-important-cves.yaml

# 4. Workloads back to their Step 1 state
envsubst < 01-inventory-cve/03-current-app.yaml | oc --context hub apply -f -
oc --context hub scale deploy/legacy-app -n acs-image-demo --replicas=1
oc --context hub wait deploy --all -n acs-image-demo --for=condition=Available --timeout=300s

# 5. Notifier, then the receiver
NOTIFIER_ID=$(curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" "https://${ACS_CENTRAL_ROUTE}/v1/notifiers" \
  | jq -r '.notifiers[] | select(.name=="workshop-alert-sink") | .id')
[ -n "${NOTIFIER_ID}" ] && curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" \
  -X DELETE "https://${ACS_CENTRAL_ROUTE}/v1/notifiers/${NOTIFIER_ID}"
oc --context hub delete -f 02-image-compliance/01-alert-sink.yaml --ignore-not-found --wait
----
