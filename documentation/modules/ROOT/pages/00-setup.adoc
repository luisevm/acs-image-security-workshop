= Cluster Setup
include::_attributes.adoc[]

This page prepares the single OpenShift cluster used in every step. You install three operators (RHACS, OpenShift GitOps, and RHACM), deploy ACS Central, and register the same cluster as an ACS secured cluster with admission enforcement turned on. The RHACM hub takes the longest to come up, so you start it early and let it finish in the background.

[#prerequisites]
== Prerequisites

* One OpenShift {ocp-version} cluster and a user with `cluster-admin`
* `oc`, `jq`, `curl`, `git`, and `envsubst` (from the `gettext` package) on your workstation
* A GitHub account, used in xref:03-policies-as-code.adoc[Step 3] to fork this repository
* Network access from your workstation to the cluster API, the cluster routes, and `registry.access.redhat.com`

IMPORTANT: ACS Central, the ACS secured cluster services, OpenShift GitOps, and the RHACM hub all run on this one cluster. Check that the worker nodes have enough free CPU and memory before you start. The workshop was validated on a cluster with one schedulable control plane node (32 vCPU, 128 GiB) and three workers (16 vCPU, 32 GiB each). With all four products running, CPU requests stayed between 32% and 61% of each node.

[#cluster-mapping]
== Cluster mapping

[cols="2,2,4",options="header"]
|===
| Role | Context name | Purpose

| Workshop cluster
| `{hub-context}`
| Runs ACS Central, the ACS secured cluster services, OpenShift GitOps, and the RHACM hub. RHACM also manages this cluster as `local-cluster`.
|===

== Option A: Prepare the cluster from scratch

Follow these sub-steps when the cluster has none of the operators yet. If someone already prepared it, go to <<option-b>>.

WARNING: Do not run sub-step 4 on a cluster where any of the three operators is already installed. The manifests create an `OperatorGroup` next to the existing one, and OLM stops reconciling a namespace that has two. They also set the subscription to the catalog's default channel, so OLM upgrades an operator that was installed from an older channel. On a pre-provisioned cluster, use <<option-b>>.

[#export-variables]
=== 2. Create `myenv.sh`

*What:* Create a personal `myenv.sh` file at the repository root with your cluster details.

*Why:* Every step reads its variables from this file, and sourcing it logs you in and names the `oc` context `{hub-context}`.

`myenv.sh` is listed in `.gitignore` because it holds your password. Create it with this content and fill in the values in angle brackets:

[source,bash]
----
# Console URL (for quick reference, not used by scripts):
# Console: https://console-openshift-console.apps.<cluster-domain>

# -- Workshop variables (used by envsubst in YAML manifests) ------------------
export OCP_API_URL="https://api.<cluster-domain>:6443"
export OCP_USER="<user>"
export OCP_PASSWORD="<password>"

export ACS_CLUSTER_NAME="workshop-cluster"          # cluster name shown in the ACS portal
export GIT_REPO_URL="https://github.com/<your-github-user>/acs-image-security-workshop.git"  # your fork (Step 3)
export GIT_REVISION="main"

# -- Context cleanup (idempotent) -------------------------------------------
oc config delete-context hub >/dev/null 2>&1

# -- Login + rename context ----------------------------------------------------
oc login "$OCP_API_URL" --username "$OCP_USER" --password "$OCP_PASSWORD" --insecure-skip-tls-verify=true
oc config rename-context "$(oc config current-context)" hub

# -- Current UBI 9 minimal image, pinned by digest (used by Step 1) -----------
export CURRENT_IMAGE="registry.access.redhat.com/ubi9/ubi-minimal@$(oc image info registry.access.redhat.com/ubi9/ubi-minimal:latest --filter-by-os=linux/amd64 -o json | jq -r .digest)"

# -- ACS values (available once Step 0 installed Central) ----------------------
if oc --context hub get route central -n stackrox >/dev/null 2>&1; then
  export ACS_CENTRAL_ROUTE="$(oc --context hub get route central -n stackrox -o jsonpath='{.spec.host}')"
  export ROX_ENDPOINT="${ACS_CENTRAL_ROUTE}:443"
  # The operator generates central-htpasswd unless the Central CR names its own adminPasswordSecret
  ROX_PW_SECRET="$(oc --context hub get central stackrox-central-services -n stackrox -o jsonpath='{.spec.central.adminPasswordSecret.name}')"
  export ACS_ADMIN_PASSWORD="$(oc --context hub get secret "${ROX_PW_SECRET:-central-htpasswd}" -n stackrox -o jsonpath='{.data.password}' | base64 -d)"
fi
# API token written by Step 0 (gitignored file); roxctl reads ROX_ENDPOINT and ROX_API_TOKEN
if [ -f .rox-token ]; then
  export ROX_API_TOKEN="$(cat .rox-token)"
fi
# roxctl downloaded by Step 0 into the repository root
case ":$PATH:" in *":$PWD:"*) ;; *) export PATH="$PWD:$PATH" ;; esac
----

The ACS variables stay empty until Central exists. Source the file again after each part of this setup that creates one of them.

[cols="2,3,4",options="header"]
|===
| Variable | Used in | Description

| `OCP_API_URL`, `OCP_USER`, `OCP_PASSWORD`
| `myenv.sh`
| Cluster API URL and credentials

| `ACS_CLUSTER_NAME`
| `00-setup/04-secured-cluster.yaml`, `05-acs-acm/03-policy-acs-baseline.yaml`
| Name of the cluster in the ACS portal

| `GIT_REPO_URL`, `GIT_REVISION`
| `03-policies-as-code/02-application.yaml`
| Your fork and the branch Argo CD follows

| `CURRENT_IMAGE`
| `01-inventory-cve/02-images.yaml`
| Current UBI 9 minimal image, referenced by digest. Step 1 builds `current-app:2.0.0` from it

| `ACS_CHANNEL`, `GITOPS_CHANNEL`, `ACM_CHANNEL`
| `00-setup/01-acs-operator.yaml`, `05-gitops-operator.yaml`, `06-acm-operator.yaml`
| Operator channels, read from the cluster catalog in sub-step 4

| `ACS_CENTRAL_ROUTE`, `ROX_ENDPOINT`
| `curl` and `roxctl` commands
| Host name of the ACS portal and API

| `ACS_ADMIN_PASSWORD`, `ROX_API_TOKEN`
| `curl` and `roxctl` commands
| ACS admin password and an API token with the Admin role
|===

IMPORTANT: Never commit `myenv.sh` or `.rox-token`. Both are in `.gitignore`.

NOTE: The admin password variable is called `ACS_ADMIN_PASSWORD` on purpose. `roxctl` reads `ROX_ADMIN_PASSWORD` from the environment, and with both that variable and `ROX_API_TOKEN` set it fails with `cannot use basic and token-based authentication at the same time`.

If the cluster was prepared by someone else (<<option-b>>), set `ACS_CLUSTER_NAME` to the name the cluster already has under *Platform Configuration > Clusters* in the ACS portal. The validation cluster used for this workshop was registered as `production`, and the outputs on these pages show that name.

.Verify: The file parses
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
bash -n myenv.sh && echo "myenv.sh syntax OK"
----

[.console-output]
[source,bash]
----
myenv.sh syntax OK
----
====

[#login-clusters]
=== 3. Log in to the cluster

*What:* Source `myenv.sh` to log in and create the `{hub-context}` context.

*Why:* Every `oc` command in the workshop uses `--context {hub-context}`, so the context name has to exist before anything else runs.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
source myenv.sh
----

NOTE: The API server of a lab cluster usually presents a certificate signed by the cluster's internal CA (`kube-apiserver-lb-signer`). Without `--insecure-skip-tls-verify=true`, `oc login` stops with `The server uses a certificate signed by unknown authority`, so `myenv.sh` passes the flag. In production, pass the cluster CA with `--certificate-authority` instead.

.Verify: You are logged in as a cluster administrator
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc whoami --context {hub-context}
oc auth can-i '*' '*' --all-namespaces --context {hub-context}
echo "CURRENT_IMAGE=${CURRENT_IMAGE}"
----

[.console-output]
[source,bash]
----
admin
yes
CURRENT_IMAGE=registry.access.redhat.com/ubi9/ubi-minimal@sha256:68b92732accbffdd8e2491b4c29976634ed92459f5779dac2aad670c967337c7
----

The digest changes whenever Red Hat publishes a new UBI 9 minimal image.

[#install-operators]
=== 4. Install the RHACS, OpenShift GitOps, and RHACM operators

icon:clock[] ~1.5 minutes (subscription to CSV `Succeeded`: RHACS 41s, OpenShift GitOps 51s, RHACM 85s, running in parallel)

*What:* Read the default channel of each operator from the cluster catalog and create the three subscriptions.

*Why:* All three operators install in parallel, which saves time, and reading the channel from the catalog avoids hard-coding a version that might not exist in your catalog.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
export ACS_CHANNEL=$(oc --context {hub-context} get packagemanifest rhacs-operator -n openshift-marketplace -o jsonpath='{.status.defaultChannel}')
export GITOPS_CHANNEL=$(oc --context {hub-context} get packagemanifest openshift-gitops-operator -n openshift-marketplace -o jsonpath='{.status.defaultChannel}')
export ACM_CHANNEL=$(oc --context {hub-context} get packagemanifest advanced-cluster-management -n openshift-marketplace -o jsonpath='{.status.defaultChannel}')
echo "ACS=${ACS_CHANNEL} GITOPS=${GITOPS_CHANNEL} ACM=${ACM_CHANNEL}"
----

The manifests contain `$\{ACS_CHANNEL}`-style placeholders, so you pipe them through `envsubst`. A plain `oc apply -f` would send the placeholders as literal text.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
envsubst < 00-setup/01-acs-operator.yaml | oc --context {hub-context} apply -f -
envsubst < 00-setup/05-gitops-operator.yaml | oc --context {hub-context} apply -f -
envsubst < 00-setup/06-acm-operator.yaml | oc --context {hub-context} apply -f -
----

Wait until each operator reports `Succeeded`. The loop waits for the CSV that each subscription installed, because a namespace also lists copies of the CSVs of operators installed for all namespaces:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
for sub in rhacs-operator/rhacs-operator \
           openshift-gitops-operator/openshift-gitops-operator \
           open-cluster-management/advanced-cluster-management; do
  ns=${sub%/*}; name=${sub#*/}
  until csv=$(oc --context {hub-context} get subscriptions.operators.coreos.com "$name" -n "$ns" \
      -o jsonpath='{.status.installedCSV}') && [ -n "$csv" ]; do sleep 5; done
  oc --context {hub-context} wait csv/"$csv" -n "$ns" \
    --for=jsonpath='{.status.phase}'=Succeeded --timeout=600s
done
----

NOTE: Once RHACM is installed, the short name `subscription` resolves to the RHACM application `Subscription` (`subscriptions.apps.open-cluster-management.io`). The commands here use the full name `subscriptions.operators.coreos.com` for that reason.

.Verify: Three operators are installed
[%collapsible]
====
[.console-input]
[source,bash,subs="+macros,+attributes"]
----
oc --context {hub-context} get subscriptions.operators.coreos.com -A | grep -E 'rhacs-operator|openshift-gitops-operator|advanced-cluster-management'
----

[.console-output]
[source,bash]
----
open-cluster-management     advanced-cluster-management   advanced-cluster-management   redhat-operators   release-2.17
openshift-gitops-operator   openshift-gitops-operator     openshift-gitops-operator     redhat-operators   latest
rhacs-operator              rhacs-operator                rhacs-operator                redhat-operators   stable
----

The last column is the channel. It shows the catalog default at the time you install, so yours can differ.
====

[#roxctl-token]
=== 7. Download `roxctl` and create an API token

icon:clock[] ~15 seconds (about 7s to download the 100 MB `roxctl` binary, 8s to source `myenv.sh` again)

*What:* Download the `roxctl` binary that matches your Central version and create an API token with the Admin role.

*Why:* The CLI checks in later steps use `roxctl`, and the `curl` calls to the ACS API need a token.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
OS=$(uname -s | tr '[:upper:]' '[:lower:]')
ARCH=$(uname -m | sed -e 's/x86_64/amd64/' -e 's/aarch64/arm64/')
curl -sk -u "admin:${ACS_ADMIN_PASSWORD}" -o roxctl \
  "https://${ACS_CENTRAL_ROUTE}/api/cli/download/roxctl-${OS}-${ARCH}"
chmod +x roxctl

curl -sk -u "admin:${ACS_ADMIN_PASSWORD}" \
  "https://${ACS_CENTRAL_ROUTE}/v1/apitokens/generate" \
  -d '{"name":"acs-image-workshop","roles":["Admin"]}' | jq -r .token > .rox-token
source myenv.sh
----

Central serves `roxctl-linux-amd64`, `roxctl-linux-arm64`, `roxctl-darwin-amd64`, and `roxctl-darwin-arm64`. There is no plain `roxctl-darwin` file.

NOTE: The workshop uses `--insecure-skip-tls-verify` with `roxctl` and `-k` with `curl` because a newly installed Central uses a self-signed certificate. In production, configure the clients to trust the Central CA instead.

[#secure-cluster]
=== 8. Register the cluster as an ACS secured cluster

icon:clock[] ~2 minutes (custom resource `Deployed` after 23s, Sensor ready after about 30s, the last of the three admission controller pods after 2 minutes)

*What:* Generate an init bundle, apply it, and create the `SecuredCluster` custom resource with admission enforcement turned on.

*Why:* The secured cluster services (Sensor, the admission controller, and Collector) report what runs on the cluster and enforce the policies at admission time.

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
roxctl --insecure-skip-tls-verify central init-bundles generate "${ACS_CLUSTER_NAME}" \
  --output-secrets "${ACS_CLUSTER_NAME}-init-bundle.yaml"
oc --context {hub-context} apply -n stackrox -f "${ACS_CLUSTER_NAME}-init-bundle.yaml"
----

IMPORTANT: The init bundle holds certificates tied to this Central instance. The file is gitignored. If you recreate Central, generate a new bundle.

The `SecuredCluster` manifest uses `$\{ACS_CLUSTER_NAME}`, so apply it through `envsubst`:

[.console-input]
[source,bash,subs="+macros,+attributes"]
----
envsubst < 00-setup/04-secured-cluster.yaml | oc --context {hub-context} apply -f -
oc --context {hub-context} wait securedcluster/stackrox-secured-cluster-services -n stackrox \
  --for=condition=Deployed --timeout=900s
oc --context {hub-context} rollout status deploy/sensor -n stackrox --timeout=600s
oc --context {hub-context} rollout status deploy/admission-control -n stackrox --timeout=600s
----

The manifest sets three admission controller options:

* `enforcement: Enabled` turns on hard enforcement through the validating webhook. It is the default for new installations since RHACS 4.9, and the `listenOn*` fields used by older guides are deprecated.
* `contactImageScanners: ScanIfMissing` lets the admission controller scan an image it has not seen before. Without it, decisions about CVEs and image age only use scan results that Central already has.
* `bypass: BreakGlassAnnotation` allows the `admission.stackrox.io/break-glass` annotation used in xref:02-image-compliance.adoc#break-glass[Step 2]. Every bypass is recorded as a violation.

In the ACS portal, open *Platform Configuration > Clusters*. The *Cluster status* column shows `Healthy` once Sensor is connected.

== Reset

The workshop resets never remove this setup. Use these commands only to remove everything from the cluster. The `delete_operator` function deletes only the CSV that each subscription installed. A namespace also lists copies of the CSVs of operators installed for all namespaces, and `oc delete csv --all` would remove those copies as well. They run in reverse order: the hub and the secured cluster go first because they depend on their operators, and Central goes after the secured cluster that reports to it.

[.console-input]
[source,bash]
----
# Deletes one operator: its subscription, then only the CSV that the subscription installed
delete_operator() {
  csv=$(oc --context hub get subscriptions.operators.coreos.com "$2" -n "$1" \
    -o jsonpath='{.status.installedCSV}' 2>/dev/null)
  oc --context hub delete subscriptions.operators.coreos.com "$2" -n "$1" --ignore-not-found
  if [ -n "$csv" ]; then oc --context hub delete csv "$csv" -n "$1" --ignore-not-found; fi
}

# 1. RHACM hub, then the RHACM operator
oc --context hub delete multiclusterhub multiclusterhub -n open-cluster-management --ignore-not-found --wait
delete_operator open-cluster-management advanced-cluster-management
oc --context hub delete namespace open-cluster-management --ignore-not-found

# 2. Secured cluster services, init bundle secrets, then Central
oc --context hub delete securedcluster stackrox-secured-cluster-services -n stackrox --ignore-not-found --wait
oc --context hub delete -n stackrox -f "${ACS_CLUSTER_NAME}-init-bundle.yaml" --ignore-not-found
oc --context hub delete central stackrox-central-services -n stackrox --ignore-not-found --wait
oc --context hub delete namespace stackrox --ignore-not-found

# 3. Operators
delete_operator openshift-gitops-operator openshift-gitops-operator
oc --context hub delete namespace openshift-gitops openshift-gitops-operator --ignore-not-found
delete_operator rhacs-operator rhacs-operator
oc --context hub delete namespace rhacs-operator --ignore-not-found

# 4. Local files
rm -f roxctl .rox-token "${ACS_CLUSTER_NAME}-init-bundle.yaml"
----
