RHACS Image Security Workshop

Step 1 left you with a policy that reports. In this step you add three image rules: no latest tag, only approved registries, and no image older than 365 days. All four policies send their violations to a webhook receiver running in the cluster. You run them in inform mode first, so you can see what they would catch, then switch them to enforce and watch the admission controller reject new deployments, updates, and scaling of workloads that break them. You finish with the break-glass annotation, which lets an emergency deployment through and records that it happened.

Prerequisites

  • Step 1 completed: legacy-app and current-app run in acs-image-demo and the CVE policy exists

  • source myenv.sh run in your current shell

How it works

The policies cover two lifecycle stages. At the BUILD stage, roxctl image check and roxctl deployment check evaluate them on demand. At the DEPLOY stage, the ACS admission controller (a validating webhook) evaluates every create, update, and scale request in scope.

A policy without enforcement actions only creates violations and notifications. Adding enforcement actions makes ACS act: FAIL_BUILD_ENFORCEMENT makes roxctl image check exit with an error, the FAIL_DEPLOYMENT_* actions make the admission controller reject the request, and SCALE_TO_ZERO_ENFORCEMENT lets Sensor scale a violating deployment to zero replicas if it gets past admission, for example after a webhook timeout.

Run oc --context hub explain securitypolicy.spec.enforcementActions to list every action the SecurityPolicy resource accepts.

Steps to apply

1. Set up an alert receiver

~30 seconds the first time on a cluster (the pull of the Python image), about 5 seconds when the image is cached

What: Deploy a small webhook receiver in acs-alert-sink and register it in ACS as a generic webhook notifier named workshop-alert-sink.

Why: Alerting means someone is told without opening the ACS portal. In a real setup the notifier points to Slack, a SIEM, or a ticketing tool. Here it points to a pod whose log you can read.

oc --context hub apply -f 02-image-compliance/01-alert-sink.yaml
oc --context hub wait deploy/alert-sink -n acs-alert-sink \
  --for=condition=Available --timeout=300s

The notifier definition contains ${ACS_CENTRAL_ROUTE}, so it goes through envsubst before it is sent to the API:

envsubst < 02-image-compliance/02-notifier.json \
  | curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" -H "Content-Type: application/json" \
    -X POST "https://${ACS_CENTRAL_ROUTE}/v1/notifiers" -d @- | jq '{id, name, type}'
Verify: The notifier exists and Central can reach the receiver 
curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" "https://${ACS_CENTRAL_ROUTE}/v1/notifiers" \
  | jq -r '.notifiers[] | [.name, .type] | @tsv'
workshop-alert-sink	generic

Send a test message through the notifier and read it in the receiver’s log:

NOTIFIER_ID=$(curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" "https://${ACS_CENTRAL_ROUTE}/v1/notifiers" \
  | jq -r '.notifiers[] | select(.name=="workshop-alert-sink") | .id')
envsubst < 02-image-compliance/02-notifier.json | jq --arg id "${NOTIFIER_ID}" '. + {id: $id}' \
  | curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" -H "Content-Type: application/json" \
    -X POST "https://${ACS_CENTRAL_ROUTE}/v1/notifiers/test" -d @-
oc --context hub logs deploy/alert-sink -n acs-alert-sink --tail=1
{}
ALERT policy='This is a test message created to test integration with StackRox.' deployment=None namespace=None stage='DEPLOY'

3. Check a manifest before deploying it

~15-30 seconds (the check scans the image in the manifest first)

What: Run roxctl deployment check on a manifest that uses the latest tag.

Why: Developers and pipelines can see a policy result before they touch the cluster.

The --cluster flag makes the check use the policy scopes and namespace context of your cluster, so the workshop policies scoped to acs-image-demo apply:

roxctl --insecure-skip-tls-verify deployment check --cluster "${ACS_CLUSTER_NAME}" \
  -f 02-image-compliance/tests/bad-latest.yaml --output json > /tmp/deployment-check.json
echo "exit code: $?"
jq -r '.results[].violatedPolicies[] | [.name, .severity, .failingCheck] | @tsv' /tmp/deployment-check.json
Verify: The latest-tag policy is listed

The output lists Workshop - Image uses the latest tag. The policies are still in inform mode, so failingCheck is false and the exit code is 0. Built-in policies, including Latest tag, show up as well.

exit code: 0
Container with privilege escalation allowed	MEDIUM	false
Pod Service Account Token Automatically Mounted	MEDIUM	false
Workshop - Image uses the latest tag	MEDIUM	false
Docker CIS 4.1: Ensure That a User for the Container Has Been Created	LOW	false
Latest tag	LOW	false
Red Hat Package Manager in Image	LOW	false

roxctl also prints a WARN line about deployments without a namespace. The test manifest sets namespace: acs-image-demo, so you can ignore it.

In the second validation run, a few hours later, the list also had Fixable Severity at least Important and Workshop - Fixable CVEs of severity Important or higher. Red Hat had published a fix for an openssl-libs CVE in the meantime, and the UBI 9 minimal image behind latest did not include it yet. CVE results change with the published data, so your list can differ.

4. Deploy a workload and get alerted

~15 seconds (deployment available after 9s, alert in the receiver’s log after 14s)

What: Deploy the latest-tag workload and read the alert in the receiver’s log.

Why: In inform mode the workload runs, and the team still gets told about it.

oc --context hub apply -f 02-image-compliance/tests/bad-latest.yaml
oc --context hub wait deploy/bad-latest -n acs-image-demo \
  --for=condition=Available --timeout=180s

After a few seconds, read the receiver’s log:

oc --context hub logs deploy/alert-sink -n acs-alert-sink --tail=20
Verify: The workload runs and the alert arrived

The log has one ALERT line per new violation of a workshop policy: the test message from sub-step 1, the image-age violation of legacy-app raised in sub-step 2, and the latest-tag violation of bad-latest.

ALERT policy='This is a test message created to test integration with StackRox.' deployment=None namespace=None stage='DEPLOY'
ALERT policy='Workshop - Image older than 365 days' deployment='legacy-app' namespace='acs-image-demo' stage='DEPLOY'
ALERT policy='Workshop - Image uses the latest tag' deployment='bad-latest' namespace='acs-image-demo' stage='DEPLOY'

The CVE violation of legacy-app is not in the log. It already existed in Step 1, and ACS notifies when a violation is raised, not when a notifier is added to its policy later.

5. Switch the policies to enforce

What: Apply the enforced version of the four policies.

Why: Once the inform results look right, enforcement stops new risk from reaching the cluster.

oc --context hub apply -f 02-image-compliance/enforce/
oc --context hub get deploy -n acs-image-demo

The enforced files differ from the inform files only by the enforcementActions list. Compare them with diff 02-image-compliance/policies/01-policy-latest-tag.yaml 02-image-compliance/enforce/01-policy-latest-tag.yaml.

The admission controller started to reject new latest-tag deployments about five seconds after the apply on the validation cluster.

Turning on enforcement does not touch workloads that already run. legacy-app and bad-latest stayed at 1/1 after the switch, although the policies include SCALE_TO_ZERO_ENFORCEMENT. Their existing violations stay active, and enforcement applies the next time someone creates, updates, or scales them. Review the inform-mode violations before you enforce, and fix or remove the workloads that would be blocked.
Verify: The policies now have enforcement actions 
oc --context hub get securitypolicies -n stackrox -l workshop=acs-image-workshop \
  -o custom-columns='NAME:.metadata.name,ACTIONS:.spec.enforcementActions'
NAME                              ACTIONS
workshop-fixable-important-cves   [FAIL_BUILD_ENFORCEMENT FAIL_DEPLOYMENT_CREATE_ENFORCEMENT FAIL_DEPLOYMENT_UPDATE_ENFORCEMENT SCALE_TO_ZERO_ENFORCEMENT]
workshop-image-age                [FAIL_BUILD_ENFORCEMENT FAIL_DEPLOYMENT_CREATE_ENFORCEMENT FAIL_DEPLOYMENT_UPDATE_ENFORCEMENT SCALE_TO_ZERO_ENFORCEMENT]
workshop-latest-tag               [FAIL_BUILD_ENFORCEMENT FAIL_DEPLOYMENT_CREATE_ENFORCEMENT FAIL_DEPLOYMENT_UPDATE_ENFORCEMENT SCALE_TO_ZERO_ENFORCEMENT]
workshop-trusted-registries       [FAIL_BUILD_ENFORCEMENT FAIL_DEPLOYMENT_CREATE_ENFORCEMENT FAIL_DEPLOYMENT_UPDATE_ENFORCEMENT SCALE_TO_ZERO_ENFORCEMENT]

6. Try non-compliant creates

What: Delete the latest workload and create it again, then try to create a workload from Docker Hub.

Why: The admission controller stops a workload that breaks an enforced rule before any pod starts.

oc --context hub delete -f 02-image-compliance/tests/bad-latest.yaml --ignore-not-found
oc --context hub apply -f 02-image-compliance/tests/bad-latest.yaml
oc --context hub apply -f 02-image-compliance/tests/bad-registry.yaml

Both apply commands fail. The error message comes from the ACS webhook and names the violated policy and its remediation text. The registry rejection looks like this:

Error from server (Failed currently enforced policies from RHACS): error when creating "02-image-compliance/tests/bad-registry.yaml": admission webhook "policyeval.stackrox.io" denied the request:
The attempted operation violated one or more enforced policies, described below:

Policy: Workshop - Image from an unapproved registry
- Description:
    ↳ Image is pulled from a registry that is not on the approved list.
- Rationale:
    ↳ Images from unvetted registries have no known provenance or security errata.
- Remediation:
    ↳ Use images from registry.access.redhat.com, registry.redhat.io, quay.io, or the
      internal OpenShift registry.
- Violations:
    - Container 'app' has image with registry 'docker.io'


2 additional policies depend on image enrichment results and will be evaluated only after the above violations are addressed.

In case of emergency, add the annotation {"admission.stackrox.io/break-glass": "ticket-1234"} to your deployment with an updated ticket number

The bad-latest rejection has the same shape, with the policy Workshop - Image uses the latest tag and the violation Container 'app' has image with tag 'latest'.

The registry and tag checks only read the image reference, so they run before any image pull or scan, and Docker Hub pull limits do not matter here. The two policies that need scan data (CVEs and image age) wait until those violations are fixed, as the last lines of the message say.

Each rejected request is also recorded as a violation with the state Attempted (the Attempted tab on the Violations page) and sent to the notifier.

Verify: Neither workload exists 
oc --context hub get deploy -n acs-image-demo
NAME          READY   UP-TO-DATE   AVAILABLE   AGE
current-app   1/1     1            1           11m
legacy-app    1/1     1            1           11m

7. Try updates and scaling

What: Point current-app at the latest tag, scale legacy-app, and restart current-app unchanged.

Why: Enforcement also covers changes to existing workloads, and a compliant change has to keep working.

# Update to a non-compliant image: rejected
oc --context hub set image deploy/current-app -n acs-image-demo \
  app=registry.access.redhat.com/ubi9/ubi-minimal:latest

# Scale a workload that already violates the CVE and age policies: rejected
oc --context hub scale deploy/legacy-app -n acs-image-demo --replicas=2

# Restart a compliant workload: allowed
oc --context hub rollout restart deploy/current-app -n acs-image-demo
oc --context hub rollout status deploy/current-app -n acs-image-demo --timeout=180s

The scale request is rejected because the image of legacy-app breaks the two policies that use scan data. The message lists each fixable CVE with the version that fixes it (trimmed):

Error from server (Failed currently enforced policies from RHACS): admission webhook "policyeval.stackrox.io" denied the request:
The attempted operation violated one or more enforced policies, described below:

Policy: Workshop - Image older than 365 days
...
- Violations:
    - Container 'app' has image created at 2021-10-26 13:03:40 (UTC)

Policy: Workshop - Fixable CVEs of severity Important or higher
...
- Violations:
    - Fixable CVE-2018-25032 (CVSS 8.2) (severity Important) found in component 'zlib' (version 1.2.11-17.el8) in container 'app', resolved by version 0:1.2.11-18.el8_5
    - Fixable CVE-2022-0778 (CVSS 7.5) (severity Important) found in component 'openssl-libs' (version 1:1.1.1g-15.el8_3) in container 'app', resolved by version 1:1.1.1k-6.el8_5
...
The restart of current-app is compliant only while its UBI 9 minimal image has no fixable Important or Critical CVE. When Red Hat publishes a fix that the image does not include yet, the CVE policy rejects the restart as well, until a rebuilt image is out and you redeploy with a new CURRENT_IMAGE. On the validation date, a fix for an openssl-libs CVE appeared between the two runs. The restart still went through because Central had not rescanned the image yet.
Verify: Only the compliant restart went through 
oc --context hub get deploy -n acs-image-demo \
  -o custom-columns='NAME:.metadata.name,REPLICAS:.spec.replicas,IMAGE:.spec.template.spec.containers[0].image'

current-app   1          registry.access.redhat.com/ubi9/ubi-minimal@sha256:68b92732accbffdd8e2491b4c29976634ed92459f5779dac2aad670c967337c7

8. Fail the build-time check

What: Run the Step 1 roxctl image check again.

Why: With FAIL_BUILD_ENFORCEMENT set, the same rule now stops a pipeline, so a non-compliant image fails before anyone tries to deploy it.

roxctl --insecure-skip-tls-verify image check --image registry.access.redhat.com/ubi8/ubi:8.4 \
  --output json > /tmp/image-check.json
echo "exit code: $?"
jq -r '.results[].violatedPolicies[] | [.name, .severity, .failingCheck] | @tsv' /tmp/image-check.json
Verify: The workshop policies now fail the check

In Step 1 only the built-in policy had failingCheck set to true. Now the two workshop policies that the legacy image violates have it as well:

ERROR:	checking image failed: failed policies found: 3 policies violated that are failing the check
exit code: 1
Fixable Severity at least Important	HIGH	true
Workshop - Fixable CVEs of severity Important or higher	HIGH	true
90-Day Image Age	LOW	false
Docker CIS 4.1: Ensure That a User for the Container Has Been Created	LOW	false
Red Hat Package Manager in Image	LOW	false
Workshop - Image older than 365 days	LOW	true

9. Use the break-glass bypass

What: Deploy the latest workload again with the admission.stackrox.io/break-glass annotation.

Why: In an emergency you may need to deploy despite a policy. The annotation lets the deployment through and ACS records the bypass for later review.

oc --context hub apply -f 02-image-compliance/tests/breakglass-latest.yaml
oc --context hub get deploy breakglass-latest -n acs-image-demo

The annotation value (TICKET-1234 here) should point to the change or incident ticket that justified the bypass.

curl -skG -H "Authorization: Bearer ${ROX_API_TOKEN}" "https://${ACS_CENTRAL_ROUTE}/v1/alerts" \
  --data-urlencode "query=Namespace:acs-image-demo" \
  | jq -r '.alerts[] | select(.state == "ACTIVE") | select(.deployment.name == "breakglass-latest") | [.policy.name, .state] | @tsv'

The built-in policy Emergency Deployment Annotation is enabled by default and records every use of the annotation. The workshop latest-tag policy also reports the deployment, and its alert lists SCALE_TO_ZERO_ENFORCEMENT. On the validation cluster, breakglass-latest was not scaled down and still ran at 1/1 90 seconds later.

Verify: The deployment was admitted and the bypass is on record

The list includes Emergency Deployment Annotation.

Emergency Deployment Annotation	ACTIVE
Latest tag	ACTIVE
Workshop - Image uses the latest tag	ACTIVE
Red Hat Package Manager in Image	ACTIVE
Container with privilege escalation allowed	ACTIVE
Docker CIS 4.1: Ensure That a User for the Container Has Been Created	ACTIVE
Pod Service Account Token Automatically Mounted	ACTIVE

Remove the bypass deployment:

oc --context hub delete -f 02-image-compliance/tests/breakglass-latest.yaml --ignore-not-found

What this solves

Problem from Step 1 How this step solves it

Nobody is notified when a violation appears

Every workshop policy sends its violations to a notifier

Vulnerable, outdated, or untrusted images can still be deployed

The admission controller rejects creates, updates, and scaling that break an enforced policy

A pipeline can still build and push a non-compliant image

roxctl image check exits with an error when an enforced policy is violated

What this does NOT solve (yet)

Remaining problem Addressed in

The policies are applied by hand with oc apply, with no review and no record of who changed what

Alternatives considered

Approach Notes

ACS policies with admission enforcement (this step)

Can use image content (CVEs, image age) as well as the image reference. Uses the scan data ACS already has.

OPA Gatekeeper, Kyverno, or ValidatingAdmissionPolicy

Good at rules on the pod spec, such as the tag or the registry. CVE or image-age decisions need an external data source.

OpenShift image policy (image.config.openshift.io allowed registries)

Restricts registries for the whole cluster at the node level. Has no per-namespace scope and no CVE criteria.

Reset

This returns the cluster to the state at the end of Step 1. The test workloads go first, then the three new policies, then the CVE policy goes back to its Step 1 version without the notifier. The notifier and the receiver go last, because Central should not hold a policy that points to a deleted notifier.

# 1. Test workloads (some were never created)
oc --context hub delete -f 02-image-compliance/tests/ --ignore-not-found

# 2. Policies added in this step
oc --context hub delete securitypolicy workshop-latest-tag workshop-trusted-registries workshop-image-age \
  -n stackrox --ignore-not-found

# 3. CVE policy back to the Step 1 version (inform only, no notifier)
oc --context hub apply -f 01-inventory-cve/04-policy-fixable-important-cves.yaml

# 4. Workloads back to their Step 1 state
envsubst < 01-inventory-cve/03-current-app.yaml | oc --context hub apply -f -
oc --context hub scale deploy/legacy-app -n acs-image-demo --replicas=1
oc --context hub wait deploy --all -n acs-image-demo --for=condition=Available --timeout=300s

# 5. Notifier, then the receiver
NOTIFIER_ID=$(curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" "https://${ACS_CENTRAL_ROUTE}/v1/notifiers" \
  | jq -r '.notifiers[] | select(.name=="workshop-alert-sink") | .id')
# Retries until config-controller has removed the notifier from the CVE policy in Central
[ -n "${NOTIFIER_ID}" ] && until [ "$(curl -sk -o /dev/null -w '%{http_code}' \
  -H "Authorization: Bearer ${ROX_API_TOKEN}" -X DELETE \
  "https://${ACS_CENTRAL_ROUTE}/v1/notifiers/${NOTIFIER_ID}")" = 200 ]; do sleep 2; done
oc --context hub delete -f 02-image-compliance/01-alert-sink.yaml --ignore-not-found --wait

oc apply of the Step 1 file removes the notifiers field from the CVE policy, because oc apply deletes fields that were in the last applied version and are missing from the new file. After that, nothing in Central refers to the notifier and the delete succeeds.
