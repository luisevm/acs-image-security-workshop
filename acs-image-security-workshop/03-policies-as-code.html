Step 3 - Policies as Code: Manage ACS policies with Argo CD

At the end of Step 2 the four policies are custom resources that you applied by hand. Anyone with access to the stackrox namespace or the ACS portal can change them, and nothing records why. In this step OpenShift GitOps (Argo CD) takes over the policies from the 03-policies-as-code/policies/ folder of your fork. You change a policy with a Git commit, watch Argo CD undo a manual change on the cluster, see how the ACS portal treats a policy it does not own, and delete and restore a policy through Git.

Prerequisites

  • Step 2 completed, with the four policies in enforce mode

  • OpenShift GitOps installed in Cluster Setup

  • A local clone of your fork, with permission to push to the branch in GIT_REVISION

  • source myenv.sh run in your current shell

How it works

Two controllers work in sequence. Argo CD keeps the SecurityPolicy custom resources in stackrox equal to the files in Git. The RHACS config-controller copies each custom resource into Central and marks the policy in the portal as managed externally. A change that starts in Git reaches Central through both controllers. A manual change to a custom resource is reverted by Argo CD self-heal. A change made in the portal stays in Central until the custom resource changes again, for example with the next commit. config-controller then writes the whole policy from the custom resource and the portal change is gone.

The files in 03-policies-as-code/policies/ carry the same names and content as 02-image-compliance/enforce/, so Argo CD adopts the existing resources without changing how ACS behaves.

Steps to apply

1. Check your fork

What: Confirm that GIT_REPO_URL is your fork, that Argo CD can read it, and that you can push to it.

Why: Argo CD reads the policies from this repository, and every change in this step is a push.

echo "${GIT_REPO_URL} ${GIT_REVISION}"
git ls-remote "${GIT_REPO_URL}" "${GIT_REVISION}"
git push --dry-run origin "${GIT_REVISION}"
The workshop assumes a public fork. For a private repository, add its credentials to Argo CD as a repository secret before the next sub-steps.
Verify: The branch exists and a push would work 
https://github.com/luisevm/acs-image-security-workshop.git main

Your output shows your fork and the latest commit on your branch.

2. Grant Argo CD access to the policies

What: Create a Role in stackrox that lets the Argo CD application controller manage SecurityPolicy resources, and nothing else in that namespace.

Why: The default Argo CD instance cannot write to stackrox until you grant it access, and the Role keeps that access as narrow as the task.

oc --context hub apply -f 03-policies-as-code/01-argocd-rbac.yaml
Verify: Argo CD can create policies 
SA=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
oc --context hub auth can-i create securitypolicies.config.stackrox.io -n stackrox --as="${SA}"
oc --context hub auth can-i delete deployments -n stackrox --as="${SA}"
yes
yes

The first answer comes from the Role you just created. The second answer is no on a default OpenShift GitOps installation, whose cluster role lets the controller read every resource but not change it outside a short list of API groups. The validation cluster answered yes, because its provisioning also bound the controller to cluster-admin. Check oc --context hub get clusterrolebinding -o wide | grep argocd-application-controller to see what your cluster grants.

3. Hand the policies to Argo CD

~25-45 seconds (Application created to first sync finished; 26s and 46s in two validation runs)

What: Create an Argo CD Application that syncs 03-policies-as-code/policies/ from your fork into stackrox.

Why: From now on the files in Git decide what the policies look like.

The Application manifest uses ${GIT_REPO_URL} and ${GIT_REVISION}, so it goes through envsubst:

envsubst < 03-policies-as-code/02-application.yaml | oc --context hub apply -f -

The Application has automated sync with prune and selfHeal turned on. It has no resources finalizer, so deleting the Application later leaves the policies in place.

To see the Application in the Argo CD UI, open the application launcher (the grid icon in the top bar of the OpenShift console) and select Cluster Argo CD. Click LOG IN VIA OPENSHIFT. The first time, OpenShift asks you to authorize the service account openshift-gitops-argocd-dex-server: click Allow selected permissions. Then open the tile acs-image-policies.

Figure 1. Cluster Argo CD - acs-image-policies manages the four SecurityPolicy resources
Verify: The Application is synced and manages the four policies 
oc --context hub get applications.argoproj.io acs-image-policies -n openshift-gitops \
  -o jsonpath='{.status.sync.status} {.status.health.status}{"\n"}{.status.resources[*].name}{"\n"}'
Synced Healthy
workshop-fixable-important-cves workshop-image-age workshop-latest-tag workshop-trusted-registries
The commands in this step use the full resource name applications.argoproj.io. With RHACM installed, the short name application resolves to the Kubernetes Application resource (applications.app.k8s.io), and oc get application acs-image-policies returns NotFound.

4. Change a policy in Git

~15 seconds (custom resource updated 8s after the push, legacy-app violation resolved 12s after the commit)

What: Raise the image-age limit from 365 to 3650 days with a commit, then ask Argo CD to refresh.

Why: A commit can be reviewed and reverted, and Git records who changed the rule.

F=03-policies-as-code/policies/03-policy-image-age.yaml
sed -i.bak -e 's/"365"/"3650"/' -e 's/ 365 days/ 3650 days/g' "$F" && rm -f "$F.bak"
git diff --stat
git commit -am "Raise the workshop image age limit to 3650 days"
git push origin "${GIT_REVISION}"
oc --context hub annotate applications.argoproj.io acs-image-policies -n openshift-gitops \
  argocd.argoproj.io/refresh=hard --overwrite

The sed patterns only match the original values, so running the command twice does not change the file again. Argo CD also polls Git on its own. The refresh annotation only saves you the wait.

Version 1.0.0 of legacy-app is older than 365 days and younger than 3650 days, so its age violation resolves.

In the portal, go to Violations and filter by the namespace acs-image-demo and the policy name Workshop. Before the commit the list had two violations of legacy-app, for the CVE policy and the age policy. Now only the CVE violation is left.

Figure 2. Violations - after the commit, legacy-app only violates the CVE policy
Verify: The new value reached the cluster and Central 
oc --context hub get securitypolicy workshop-image-age -n stackrox \
  -o jsonpath='{.spec.policySections[0].policyGroups[0].values[0].value}{"\n"}'
curl -skG -H "Authorization: Bearer ${ROX_API_TOKEN}" "https://${ACS_CENTRAL_ROUTE}/v1/alerts" \
  --data-urlencode "query=Namespace:acs-image-demo+Violation State:RESOLVED" \
  | jq -r '.alerts[] | select(.policy.name | startswith("Workshop - Image older")) | [.policy.name, .deployment.name, .state] | @tsv'
3650
Workshop - Image older than 365 days	legacy-app	RESOLVED

The resolved violation keeps the policy name it had when it was raised. If you run the workshop a second time, older resolved violations show up as extra lines. Central re-evaluated legacy-app as soon as it received the changed policy. Without the Violation State:RESOLVED filter, the list also shows the ATTEMPTED violation from the rejected scale request in Step 2, which stays on record.

5. Watch Argo CD undo a manual change

What: Lower the severity of the latest-tag policy directly on the cluster and watch it come back.

Why: A change that bypasses Git does not last, so the policy in Git is the policy that runs.

oc --context hub patch securitypolicy workshop-latest-tag -n stackrox \
  --type merge -p '{"spec":{"severity":"LOW_SEVERITY"}}'
for i in $(seq 1 12); do
  oc --context hub get securitypolicy workshop-latest-tag -n stackrox -o jsonpath='{.spec.severity}{"\n"}'
  sleep 5
done
Verify: The severity returns to MEDIUM_SEVERITY

6. Try to edit the policy in the ACS portal

What: Open a workshop policy in the ACS portal and try to edit it.

Why: Participants who use the portal need to know that a policy managed as code cannot be changed there for good.

In the ACS portal, go to Platform Configuration > Policy Management and filter by the policy name Workshop. The Origin column shows Externally managed for the four workshop policies. Open Workshop - Image uses the latest tag, then open Actions. Edit policy is available, and the delete entry is disabled with the text Cannot delete an externally managed policy. Select Edit policy and read the warning at the top of the page, then click Cancel.

Figure 3. Policy Management - editing an externally managed policy
Verify: The portal shows the policy as externally managed

The edit page starts with this warning:

Externally managed policy
You are editing a policy that is managed externally. Any local changes to this policy will be automatically overwritten during the next resync.

The next resync happens when the custom resource changes, not on a timer you can count on. On the validation cluster, a severity change saved in Central was still in place 10 minutes later. It disappeared about 6 seconds after the next change to the custom resource’s spec. A change to an annotation alone did not trigger it.

7. Delete and restore a policy through Git

What: Remove the registry policy file in Git, check that the policy disappears from the cluster and from Central, then revert the commit.

Why: Deleting a rule is also a reviewed change, and git revert brings it back exactly as it was.

git rm 03-policies-as-code/policies/02-policy-trusted-registries.yaml
git commit -m "Remove the workshop registry policy"
git push origin "${GIT_REVISION}"
oc --context hub annotate applications.argoproj.io acs-image-policies -n openshift-gitops \
  argocd.argoproj.io/refresh=hard --overwrite

Check that the custom resource and the Central policy are gone:

oc --context hub get securitypolicy workshop-trusted-registries -n stackrox
curl -sk -H "Authorization: Bearer ${ROX_API_TOKEN}" "https://${ACS_CENTRAL_ROUTE}/v1/policies" \
  | jq -r '.policies[].name' | grep '^Workshop - '

Both the custom resource and the Central policy are normally gone about 10 seconds after the push, and the restore below takes about as long.

In three of four validation runs (RHACS 4.11.4), the policy disappeared from Central within seconds, but the custom resource stayed in the cluster with a deletion timestamp. config-controller deleted the policy in Central, failed to remove its finalizer because of an update conflict, and then kept failing with policy "" is not externally managed and can be deleted only from central. A plain oc delete of a test policy did not hit this. Check for it before you restore the policy.

If the first command below prints a timestamp a minute after the push, the resource is stuck. The policy is already gone from Central, so you can remove the finalizer by hand. Otherwise Argo CD cannot create the resource again in the next command.

oc --context hub get securitypolicy workshop-trusted-registries -n stackrox \
  -o jsonpath='{.metadata.deletionTimestamp}{"\n"}'
oc --context hub patch securitypolicy workshop-trusted-registries -n stackrox \
  --type=json -p '[{"op":"remove","path":"/metadata/finalizers"}]'

Run the patch command only when the get command printed a timestamp. When the resource is already gone, get returns NotFound and there is nothing to fix.

Restore it:

git revert --no-edit HEAD
git push origin "${GIT_REVISION}"
oc --context hub annotate applications.argoproj.io acs-image-policies -n openshift-gitops \
  argocd.argoproj.io/refresh=hard --overwrite
Verify: The registry policy is back in Central 
oc --context hub get securitypolicy workshop-trusted-registries -n stackrox \
  -o jsonpath='{.status.conditions[?(@.type=="AcceptedByCentral")].status}{"\n"}'
True

What this solves

Problem from Step 2 How this step solves it

Policies are applied by hand, with no review and no record of who changed what

Every change is a Git commit that Argo CD applies

Someone can edit or delete a policy and nothing puts it back

Argo CD self-heal reverts changes to the custom resources, the portal cannot delete an externally managed policy, and the next change in Git overwrites portal edits

What this does NOT solve (yet)

Remaining problem Addressed in

Admission enforcement can be turned off on the cluster, or the secured cluster services removed, and the policies stop blocking anything

Alternatives considered

Approach Notes

SecurityPolicy custom resources synced by OpenShift GitOps (this step)

Native to RHACS since policy as code became generally available in 4.8. Works with any Git server Argo CD can reach.

RHACM policy that creates the SecurityPolicy resources on the hub

Possible, since Central reads the custom resources from its own namespace. Adds a second tool for the same job when Argo CD already runs.

Scripts that call the ACS policy API from a pipeline

Works on versions without policy as code. You write and maintain the drift detection yourself.

Reset

This returns the cluster to the state at the end of Step 2 and puts the image-age file in your fork back to 365 days, so the step works again on the next run. The Application goes first so that nothing reconciles while you restore the files.

# 1. Stop Argo CD from managing the policies (no finalizer, so the policies stay)
oc --context hub delete applications.argoproj.io acs-image-policies -n openshift-gitops --ignore-not-found --wait

# 2. Remove the Argo CD permissions
oc --context hub delete -f 03-policies-as-code/01-argocd-rbac.yaml --ignore-not-found

# 3. Restore the Git files in your fork
F=03-policies-as-code/policies/03-policy-image-age.yaml
sed -i.bak -e 's/"3650"/"365"/' -e 's/ 3650 days/ 365 days/g' "$F" && rm -f "$F.bak"
P=03-policies-as-code/policies/02-policy-trusted-registries.yaml
git ls-files --error-unmatch "$P" >/dev/null 2>&1 \
  || git checkout "$(git rev-list -n 1 HEAD -- "$P")^" -- "$P"
git add 03-policies-as-code/policies/
git diff --cached --quiet || { git commit -m "Reset workshop policies to the Step 2 state"; git push origin "${GIT_REVISION}"; }

# 4. Put the cluster policies back to the Step 2 enforced state
oc --context hub apply -f 02-image-compliance/enforce/

If sub-step 7 stopped after the delete commit, the git checkout line restores the registry policy file from the commit before the last change to it, however many commits came after.
